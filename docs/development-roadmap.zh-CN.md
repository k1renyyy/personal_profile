# 个人作品集开发路线图

> 本文档不是待办清单，而是项目从开源底座走向独立个人作品集的完整建设路径。它记录项目起点、真实完成过程、计划与实际的偏差、由此形成的方法论，以及下一阶段方向。

## 一、项目目标与原则

### 项目目标

将导入的 `portfolio-v3` 开源项目逐步改造成一个能够长期维护、持续演进，并代表 Kiren 个人设计与工程能力的作品集网站。

项目不以替换姓名、图片和文案为终点，而要完成四层转变：

1. **身份转变**：从原作者的作品集变成 Kiren 的个人表达。
2. **内容转变**：从模板项目和占位内容变成真实、可信、可维护的个人内容。
3. **设计转变**：在保留有效工程底座的同时，形成独立的视觉语言、页面节奏和交互方式。
4. **工程转变**：从依赖模板历史结构的代码，收敛为边界清晰、可以安全修改和发布的个人项目。

### 长期原则

- 设计、内容、实现和发布是不同层次的工作，重要变更应先明确所属层次和边界。
- 先理解和验证现有行为，再修改；不为追求整洁破坏已经成立的体验。
- 已批准的新设计优先于历史模板，但不把局部重设计扩大为无边界的全站重写。
- 内容必须真实、可核实；缺失内容可以暂缓，不能用虚构内容填满页面。
- 复用已经证明有效的能力；失去生产用途的历史实现应及时退出。
- 测试保护用户可见行为和关键边界，不永久固化偶然的实现细节。
- 每个阶段留下与风险相匹配的验证结果，不默认保存全部过程产物。
- Roadmap 必须反映真实路径。实际决策变化后，更新计划并记录原因，不继续假装旧计划有效。
- 第三方代码、资产和设计参考必须明确边界；最终发布内容应清楚表达项目自身的归属和创作过程。

## 二、项目起点

### 开源底座

项目起点是提交 `dae2155d` 导入的 `portfolio-v3`。底座提供了：

- Next.js App Router、React、TypeScript 和 Tailwind CSS 工程结构。
- 首页、项目列表和项目详情路由。
- GSAP、Lenis、Anime.js、Framer Motion 和 Three.js 等动效能力。
- Shoot Mode、主题切换、页面转场、WebGL 和若干视觉组件。
- 原作者的项目数据、个人身份、图片、链接和部分外部服务逻辑。

选择继续使用底座，而不是立即重写，是因为它已经提供可运行的页面和复杂交互。早期工作的重点因此是识别哪些能力值得保留、哪些内容必须替换，以及个人设计应从哪里开始生长。

### 起点风险

- 视觉效果与业务逻辑、全局事件和滚动行为耦合较深。
- 多套动画技术同时存在，部分组件职责过大。
- 原作者身份、项目内容、链接和资源分散在多个位置。
- CMS、发布方式、主题和支持视口尚未确定。
- 如果持续叠加功能，后期会难以区分底座、个人设计和遗留代码。

因此第一步不是重做页面，而是建立可恢复、可比较、可验证的工程基线。

## 三、实际完成路径

以下阶段依据 2026 年 8 月 30 日至 9 月 4 日的真实 Git 历史重建，不沿用旧 roadmap 的预设阶段。

### 阶段 1：建立并稳定导入基线

**问题**

导入项目包含 Supabase 实时功能、非确定性渲染、lint 问题、依赖漏洞、主题水合差异、静态导出问题和外部请求风险。直接开始设计会难以判断问题来自底座还是新代码。

**决策与完成工作**

- 保存原始路由、截图和浏览器行为证据。
- 移除不需要的 Supabase 聊天、在线状态和协作光标。
- 分别修复 lint、React 渲染、水合、Rubik、主题和静态导出问题。
- 删除受限 GitHub 请求并处理当时已知依赖问题。
- 建立仓库规范、单元测试、浏览器回归和可恢复基线。

**结果与经验**

项目获得了可靠参照点，“先稳定后设计”的方向成立。但保存的截图和过程证据过多，后来增加了仓库体积。以后只保存能够支持决策、回归或恢复的最小证据集。

### 阶段 2：梳理内容需求并选择 CMS

**问题**

个人身份、项目、经历、媒体和 SEO 内容分散在组件与数据文件中，尚不清楚是否真正需要 CMS。

**决策与完成工作**

- 先审计页面、路由、Metadata、媒体和内容消费者。
- 建立平台中立内容模型和内容清单。
- 比较仓库内容与多个 CMS 方案。
- 根据无代码编辑、草稿、媒体管理和退出路径需求，选择 Sanity 作为唯一 PoC 候选。

**结果与经验**

内容建模帮助识别了真实数据需求，但研究规模超过当时内容量。以后应先证明编辑频率和协作需求，再决定外部内容系统的深度。

### 阶段 3：完成 Sanity PoC 与生产基础

**问题**

需要验证 Sanity 是否适合静态导出、草稿隔离、构建期查询、签名 webhook、失败恢复和内容导出。

**决策与完成工作**

- 将 Studio 作为独立子项目，不改变生产页面。
- 创建有界 PoC dataset、schema、adapter 和校验规则。
- 验证草稿隔离、服务不可用、导出、恢复和本地签名 webhook。
- 扩展正式 profile、homepage、experience、project、testimonial、socialLink 和 mediaRecord schema。
- 建立发布内容查询、运行时校验和 Studio 编辑基础。
- 将 Studio 从根项目的 TypeScript 与构建边界中隔离。

**结果与经验**

Sanity 的技术可行性得到验证，但 PoC、正式查询、repository 回退和页面专用 view model 同时保留，形成多套内容路径。技术验证完成不代表必须立即全面接入；设计快速变化时，稳定数据合同应晚于设计定稿。

### 阶段 4：替换全局个人身份

**问题**

Navbar、Hero、Contact、Footer、Metadata 和社交链接分别读取不同位置的数据，容易遗漏和不一致。

**决策与完成工作**

- 建立共享 identity view model、校验、映射和读取入口。
- 替换 Metadata、导航、Hero、Contact、Footer 和社交链接中的身份信息。
- 删除一部分原作者身份资源。
- 增加身份消费者、文案、失败回退和 Metadata 测试。

**结果与经验**

共享 view model 减少了身份重复，但项目与首页内容没有同步完成同样的收敛。“身份统一”不等于项目已经完全个人化。

### 阶段 5：建立 Experience 第一版重设计

**问题**

真实经历比模板内容更长，旧展示不足以承载公司、职位、时间和成果。

**决策与完成工作**

- 编写 Experience 设计规格、实施计划和回滚保护。
- 添加基于 Radix 的可访问 Tabs primitive。
- 实现桌面 master-detail：左侧选择公司，右侧展示单一经历。
- 补充 logo 回退、键盘、切换动画、滚动稳定和 reduced-motion 测试。

**结果与经验**

第一版解决了信息结构与可访问性，但随后被新的视觉方向替代。实现前批准可以减少误解，却不能阻止设计继续演进；方向改变时必须明确旧方案已被替代。

### 阶段 6：重新设计 Featured Work

**问题**

传统项目卡片无法表达希望呈现的作品选择感、舞台感和个人视觉风格。

**决策与完成工作**

- 放弃旧 roadmap 预设的卡片原地展开。
- 改为左侧项目序列与右侧内容舞台的 selector/stage 构图。
- 实现标题输入、内容原子更新和平滑切换。
- 保持选择行为不改变 URL 或滚动位置。
- 补充鼠标、键盘、对比度、reduced-motion 和多视口测试。
- 后续进一步简化交互和导航状态。

**结果与经验**

该阶段形成了区别于底座的个人设计语言，但测试过度锁定动画时间、尺寸和中间帧。以后优先保护内容一致性、可操作性和最终视觉。

### 阶段 7：第二轮首页整体设计演进

**问题**

Experience 和 Featured Work 单独重做后，与 Hero、About、区块过渡之间缺少统一节奏。

**决策与完成工作**

- 不再严格遵循旧 roadmap 的逐区块迁移顺序，转向整体页面体验。
- 将 Experience 从 master-detail 改为滚动驱动的三卡翻转展示。
- 继续调整 Featured Work 的详情表现。
- 重做区块间过渡、间距和视觉层次。
- 简化 Hero 控制逻辑。
- 优化 Experience 与 Project 详情呈现。
- 加入动态 About 照片拼贴，强化个人表达。

**结果与经验**

项目从“替换模板内容”进入“形成自己的作品集设计”。但旧组件、旧方案、重复依赖和历史测试没有同步退出。以后每轮设计确认后必须包含一次受控收尾。

### 阶段 8：全仓库审计与路线重建

**问题**

旧 roadmap 仍描述桌面浅色、Experience master-detail、Project 卡片展开、`cms_build` 集成和取消详情路由，已经不能解释真实代码。

**决策与完成工作**

- 停止使用旧计划约束已经变化的设计。
- 检查完整仓库、调用关系、内容来源、依赖、测试和 Git 结构。
- 确认 lint、单元测试、Studio 测试和生产构建通过。
- 识别多套内容路径、大型交互组件、滚动耦合、动画依赖重叠、旧内容资源和历史文档体积等风险。
- 按真实提交历史重建本文档。

**结果与经验**

Roadmap 从一次性实施脚本转为持续维护的方法论。未来路线以实际产品目标为中心，不再延续已经失效的 Phase 编号和预设方案。

## 四、计划与实际偏差

### 1. 桌面浅色优先变为同步探索深色和移动端

**原计划**：第一版只正式支持桌面浅色。

**实际路径**：身份、首页和局部交互已经覆盖深色与多个移动视口。

**判断**：偏离合理，因为颜色、图片、动效和组件结构会影响后续适配；但“已经涉及”不等于“已经完成统一验收”。

**方法修正**：区分设计时同步考虑与发布前正式验证，后续在 Milestone B 集中收敛。

### 2. Experience 从 master-detail 变为滚动翻牌

第一版已经完整实现并验证，随后被三列卡片、滚动展开和翻转叙事替代，移动端仍保留 Tabs 思路。

这是个人设计方向成熟后的主动替代，不是简单失败。问题在于旧实现和测试没有同步退出。以后新方案取代旧方案时，必须记录替代关系并安排清理。

### 3. Featured Work 没有采用卡片原地展开

首页最终采用 selector/stage；项目详情路由和独立项目列表仍然存在。

新方案更符合视觉语言，但首页、列表和详情页的产品关系仍需最终决定。以后应先定义“首页负责吸引、列表负责浏览、详情负责证明”的信息职责，再决定路由去留。

### 4. Sanity 从主线变成并行基础设施

原计划依次将全部生产内容迁入 Sanity，实际只有部分读取进入专用查询层，本地数据仍承担快速设计迭代。

这一偏离提高了设计速度，却留下重复模型。CMS 是编辑方式，不是产品目标；只有展示结构稳定、字段合同明确且确有编辑需求时，才完成生产迁移。

### 5. 分支阶段化没有按计划执行

原计划在 `cms_build` 完成 CMS 工作后逐级集成，实际工作主要连续沉淀在 `personal-development`，当前也没有本地 `cms_build`。

以后保持简单：`main` 保存可发布版本，`personal-development` 承载整合工作；只有高风险、可独立验收的任务才建立短期分支或 worktree。

### 6. 过程证据保存过多

完整规格、实施计划、截图、逐帧测试和回滚资料提供了可靠审计能力，也制造了重复文档、二进制历史和维护负担。

以后保留最终决策、关键基线和必要复盘；临时截图、被替代方案的细粒度测试和一次性执行计划不默认成为永久资产。

## 五、项目方法论

### 1. 用四层模型判断变更

1. **内容层**：文案、项目、经历、图片、链接和 SEO。
2. **设计层**：布局、视觉语言、信息层级、响应式和交互方案。
3. **实现层**：组件、状态、动画、数据读取、测试和配置。
4. **发布层**：远端、Preview、域名、环境变量和回滚。

一项工作可以影响多层，但必须明确主层和边界。不要借“改文案”重构组件，也不要借“清理代码”改变已批准体验。

### 2. 先建立真实基线

较大变更前：

- 确认分支和工作树。
- 找到真实调用链和数据来源。
- 记录必须保持的行为，而不是机械保存所有像素。
- 根据风险选择 lint、单测、构建或浏览器验证。

基线用于解释和恢复变化，不是为了让旧实现永远不能改变。

### 3. 设计探索与生产收敛分开

设计探索期允许快速比较方案，但要限制影响范围。方向确认后必须进入收敛期：

- 删除被替代的组件、样式和依赖。
- 更新测试，只保留仍代表产品要求的断言。
- 用真实内容验证结果。
- 更新 roadmap 中的决策与后续影响。

### 4. 内容源只能有一个生产事实来源

展示组件可以有 view model，repository 可以作为开发或回退数据，但同一内容不能长期由多个互不关联的数据文件维护。

选择内容系统时依次回答：

1. 谁会编辑？
2. 多久编辑一次？
3. 是否需要无代码、草稿、媒体管理或多人协作？
4. 静态仓库内容是否已经足够？
5. 采用 CMS 后的失败和退出路径是什么？

### 5. 测试保护结果，不保护偶然实现

优先保护页面访问、内容一致性、主要输入方式、焦点、reduced-motion、路由、滚动恢复和最终稳定视觉。

谨慎锁定动画中间帧、私有状态、DOM 包装、没有产品意义的固定时长，以及已被新设计替代的历史行为。

### 6. 新方案必须包含旧方案退出条件

批准新设计时，同时说明：

- 哪些旧组件被替代。
- 哪些测试需要更新或删除。
- 哪些依赖可能失去调用方。
- 哪些文档不再代表现状。
- 何时完成清理和最终验证。

### 7. 下次开始使用决策记录

从下一次重要方向变化开始，必须在 roadmap 对应阶段或设计规格中使用以下模板，不再维护脱离上下文的独立日志：

```text
日期：
原计划：
新决策：
变化原因：
影响范围：
后续事项：
```

需要记录：设计方案替代、路由或内容源变化、技术栈变化、阶段提前/延期/取消、发布范围变化、旧验收标准失效。普通实现细节和无产品影响的小修复不记录。

### 8. 阶段完成标准

- 目标已经实现，而不是只完成代码。
- 必要验证通过，失败项有明确结论。
- 新方案产生的旧代码、旧测试和旧依赖已处理。
- Roadmap 已反映真实结果和重要偏差。
- 下一阶段不依赖未说明的临时状态。

## 六、后续路线

后续使用四个围绕产品结果的里程碑。里程碑内部可以根据设计反馈调整顺序，但重要变化必须使用上述决策模板。

### Milestone A：完成个人化设计与真实内容

**目标**

让网站在内容、视觉和项目叙事上真正属于 Kiren，不再依赖原作者身份或模板内容支撑完整页面。

**主要工作**

- 确认 Hero、About、Experience、Featured Work、Skills、Testimonials、Contact 和 Footer 的最终职责。
- 完成 About 照片拼贴和首页整体节奏的设计验收。
- 使用真实个人经历、技能、项目、成果、链接和媒体替换模板内容。
- 明确首页 Featured Work、`/projects` 和 `/projects/[slug]` 的关系，再决定详情路由保留、重做或删除。
- 没有真实授权推荐语时隐藏 Testimonials。
- 替换包名、Metadata、旧域名、旧 GitHub 链接、旧图片和其他可见身份痕迹。
- 记录第三方代码、字体、模型、音频和资产的许可边界。

**完成标准**

- 所有公开内容真实、可核实并由所有者确认。
- 页面不再展示原作者身份、项目、账号或域名。
- 首页与项目路由的信息结构明确。
- 个人化设计在桌面主视口获得确认。
- 待补内容被隐藏或明确延期，不发布伪造占位内容。

### Milestone B：补全响应式布局和深色主题

**目标**

把已经零散实现的移动端、平板和深色能力收敛为正式支持的完整体验。

**主要工作**

- 为 `390x844`、`430x932`、`768x1024`、`1024x768`、`1440x900` 和 `1920x1080` 定义正式布局。
- 检查各区块排版、换行、间距、媒体裁切、滚动高度和横向溢出。
- 明确 Experience 在桌面翻牌与移动 Tabs 之间的切换。
- 明确 Featured Work 在窄屏上的内容顺序、选择和触摸行为。
- 验证导航、项目路由、页面转场、浏览器返回和滚动恢复。
- 完成深色主题颜色、对比度、图片、WebGL、hover、focus 和选中状态。
- 统一持续动效、触摸和 reduced-motion 方案。
- 至少检查一台真实 iOS 和一台真实 Android 设备。

**完成标准**

- 支持视口无横向溢出、不可读内容或静默裁切。
- 浅色和深色的重要文字、控件及状态清晰可读。
- 鼠标、键盘和触摸能够完成主要操作。
- reduced-motion 不依赖空间位移或无限动效表达必要状态。
- 移动端修复不造成未批准的桌面退化。

### Milestone C：收敛架构并完成工程验证

**目标**

在设计和内容稳定后删除失去用途的历史实现，降低以后修改页面的成本。

**主要工作**

- 决定 Sanity 的最终角色：生产主源、有限内容源或暂不用于前台。
- 统一首页、项目、身份和详情页的数据来源。
- 删除无生产调用方的 PoC adapter、旧组件、旧资源和对应测试。
- 收敛 Anime.js、GSAP、Framer Motion、Motion 和 Three.js 的真实使用范围。
- 删除已完成使命的滚动调试代码。
- 在保持行为的前提下降低 Shoot Mode 与全局滚动系统的耦合。
- 精简只验证动画中间帧的脆弱 E2E 断言。
- 处理依赖安全通告。
- 恢复 Playwright 浏览器环境，执行聚焦和发布前多浏览器回归。
- 检查性能、SEO、Metadata、可访问性、链接和静态资源。

**完成标准**

- 每类生产内容只有一个事实来源。
- 不存在确认无调用方的组件、资源和直接依赖。
- Lint、单元测试、Studio 测试和生产构建通过。
- Chromium、Firefox 和 WebKit 的关键路径通过。
- 没有未解释的浏览器错误、滚动锁死、损坏路由或生产依赖安全问题。
- 页面能够快速追溯到组件、数据源和测试。

### Milestone D：Preview、正式部署与上线回归

**目标**

把完成并验证的作品集作为独立个人项目安全发布，并建立最小可持续维护路径。

**主要工作**

- 确认开源许可和必要归属要求，整理仓库身份、远端和发布历史策略。
- 将可审阅版本推送到个人私有远端并创建 Preview。
- 配置正式环境变量和必要的 Sanity 读取或 webhook 能力。
- 验证静态导出、HTTPS、字体、图片、3D、音频、Metadata 和分享图。
- 配置个人域名、规范 URL、favicon、Open Graph 和索引策略。
- Preview 完成内容、视觉、响应式、主题、性能和浏览器验收后再发布 Production。
- 上线后检查首页、项目、404、外部链接、转场、滚动、Shoot Mode、声音、WebGL 和 Console/Network。
- 记录最终发布提交、日期、域名和回滚方式。

**完成标准**

- 远端、部署、页面内容和 Metadata 均使用个人项目身份。
- 第三方代码和资产的处理符合实际许可证。
- Preview 与 Production 使用同一条可重复发布路径。
- 正式域名通过 HTTPS 访问，规范 URL 和分享内容正确。
- 桌面、移动、浅色、深色和主要输入方式完成上线回归。
- 生产问题可以回退到上一份成功构建，或通过同一 Preview 流程修复。

## Roadmap 维护方式

- 已完成路径只在发现事实错误或需要补充关键复盘时修改。
- 后续路线允许演进，但方向变化必须使用方法论中的决策模板。
- 页面设计细节放在对应规格中；roadmap 只保存目标、关键决策、结果和方法。
- Git 提交记录实现过程，测试保存可执行验证，roadmap 解释为什么这样建设。
- 每完成一个里程碑，补充其真实路径与偏差，再决定下一里程碑是否调整。
