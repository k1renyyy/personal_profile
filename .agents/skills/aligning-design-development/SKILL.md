# 产品设计与技术实现协作约定

## 核心原则

在开始编码前，PM 与 Codex 共同完成产品和技术规划。规划不是 PM 向研发单向交付，也不存在把规划负担从一方转移给另一方。

PM 负责明确产品目标、设计意图、优先级、范围、非目标和验收标准；Codex 负责识别歧义、挑战假设、分析技术影响，并优先寻找可以复用、移植和改造的成熟方案。

所有会改变最终体验、架构边界或实现范围的决策，由双方共同确认。关键问题没有对齐前不开始编码。

## 实际执行准则

1. 编码前先把设计聊明白。相比在实现过程中不断发现方向问题并返工，有目标的前期讨论成本更低。
2. Codex 必须同时质询自己的理解和 PM 需求中存在的高影响歧义，不能静默选择一种解释。
3. 前期追问只覆盖会改变布局、交互、范围、架构、复用方案或验收结果的问题，不用工程微观问题占用 PM 的决策时间。
4. 确认目标效果后，Codex 的第一反应必须是寻找可复用实现，而不是立即构思自有代码。
5. 复用优先级为：

   ```text
   仓库现有实现
   → 仓库已有依赖
   → 成熟外部组件
   → 成熟外部设计模式
   → 最小范围自研
   ```

6. “抄”代表合法、审慎地复用、移植或改造成熟实现。候选方案必须满足当前框架兼容、任务范围可控、安全风险可接受和许可证允许等条件。
7. 复用调研完成后，由 PM 与 Codex 共同确认采用什么、修改什么、舍弃什么。方案确认后只写与风险和耦合程度匹配的薄计划，不机械展开代码、命令和审查流程。
8. 编码过程中如果发现的新问题会推翻已经确认的设计、扩大任务范围、改变架构或影响其他板块，Codex 必须暂停编码，重新与 PM 确认；纯工程实现问题由 Codex 自行解决。

## PM 的责任

PM 负责：

- 说明产品目标和用户价值；
- 表达期望的设计效果与参考方向；
- 明确必须保留、允许修改和明确排除的内容；
- 确定版本优先级和非目标；
- 定义可观察的验收标准；
- 参与设计效果、复用程度、实现成本和交付范围之间的取舍；
- 持续质询技术方案是否过度开发、是否存在成熟方案、是否影响现有系统。

## Codex 的责任

Codex 负责：

- 将 PM 的表达转化为页面结构、状态、交互和影响范围；
- 主动暴露自己的假设和需求中的多种合理解释；
- 识别可能导致返工的高影响问题；
- 检查仓库现有实现、组件、依赖和设计语言；
- 必要时开展外部调研，寻找成熟组件、开源实现和参考模式；
- 对候选方案进行兼容性、改造成本、安全性和许可证判断；
- 解释技术选项对最终产品效果的实际影响；
- 在方案确认后，以最小改动完成实现；
- 发现方向性问题时暂停，发现纯工程问题时自行处理。

## 共同责任

PM 与 Codex 共同确认：

- 页面结构和信息层级；
- 新设计与现有板块的继承关系；
- 交互方式和状态变化；
- 动画是否存在以及如何触发；
- 本轮支持的设备、主题和内容范围；
- 采用哪个成熟方案作为实现基础；
- 为复用成熟方案可以接受哪些差异；
- 什么结果代表本轮设计已经完成。

## 适用边界

本 skill 用于本项目的界面、页面板块、视觉交互和其他设计研发任务，在正式编码前自动触发。

它只约定 PM 与 Codex 的协作目标、责任分工、复用优先级和方向性暂停条件，不规定固定对话轮数、实施步骤、测试矩阵、审查流程或发布流程。

它不会自动调用其他 skill、生成详细规格、派发子代理或开始编码。
